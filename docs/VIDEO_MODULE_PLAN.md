| 优先级 | 范围 | 状态 | 说明 |
|---|---|---|---|
| **P0** | **影视端**：三种源（在线 CMS10 / 本地文件 / 自配插件）+ 播放器 + 字幕 | **本轮唯一开发目标** | 对应导航栏「首页 / 电影 / 动漫」三个 Tab |

### 0.2 验收标准：发布级（Release-grade）

用户明确目标为**对外发布**（打包 Setup.exe 分发给他人使用），而非仅自用。这一条改变了工程标准，以下要求全部转为**强制**：

| 维度 | 自用标准（不适用） | **发布标准（本项目采用）** |
|---|---|---|
| 错误处理 | 报错即可 | 源失效、超时、解析失败必须有降级路径与用户可读提示 |
| 源健康检查 | 无 | 聚合搜索需并发超时控制 + 失败源自动跳过，不得整体卡死 |
| 编解码兜底 | 播不了就算 | AC-3 / E-AC-3 等不支持的音轨必须有明确提示或转码兜底（详见第二章） |
| 数据迁移 | 无 | 存储结构需带 schema version，后续版本可迁移 |
| 更新系统 | 无 | 影视模块须纳入现有 electron-updater 与增量补丁体系 |
| 回归验证 | 手测 | 每 Step 结束跑 `node --check` + 三组 `node --test`，关键视觉改动配截图对比 |

1. **GPLv3 分发义务（新增，必须执行）**：对外分发 Setup.exe 时，必须同步提供**与该二进制对应的完整源码**。落地方式：每个 Release 打对应的源码 tag，Release 说明中给出源码链接。此项须写入 `RELEASE.md` 的发布流程。
2. **GSAP 授权冲突升级为发布前阻塞项**：此前评估为「该修但不急」，其前提是自用。**一旦对外分发，GPLv3 §7「不得附加额外限制」的冲突即刻成立**。GSAP 为 GreenSock 专有授权（非 OSI 开源，无 modify / sublicense 授权，可单方撤销）。当前使用面已实测：80 处调用 / 仅 6 个基础 API（`fromTo` 23 / `to` 22 / `killTweensOf` 21 / `set` 11 / `timeline` 1 / `delayedCall` 1）/ **零插件**。→ 处理时机由「影视 1.0 之后」提前至「**首个对外 Release 之前**」。

### 1.4 视觉控制台分页的双态映射（2026-07-31 确认）

**保留项（用户明确）**：视觉控制台、粒子系统、home 面板在影视空间中全部保留。变化的只有控制台内部的 tab 分区内容。

#### 现状（已核实）

控制台 `#fx-panel`（`index.html:2303`）的 5 个分页**不是写死的 HTML**，而是运行时生成：

- 分页定义：`organizeFxPanel()` 内的 `tabMeta` 数组（`index.html:25760`），5 项 = 预设 / 外观 / 歌词 / 动态 / 高级；

- **一次性守卫**：`panel._fxPanelOrganized`（`:25758`）使该函数只执行一次，**切换空间时不会重新分配控件**——这是双态切换必须处理的技术点。

#### 双态对照

| 分页 | 音乐空间（现状） | 影视空间 | 判定 |

## 二、调研确认的事实（已验证，非假设）

### 2.1 可复用底座
- Electron `^42.4.1`，`WebContentsView` API 可用（Electron 30+ 稳定）。
- `server.js:7772-7773` 静态兜底会把任意路径映射到 `public/`，**`public/video.html` 无需改配置即可访问**。
- `package.json:35` 的 `"public/**/*"` 已通配，新文件自动进打包。
- `server.js:7784-7786` 已有 `server.setCustomSourceBridge` 挂载外部桥接的范式，可照此扩展。
- `desktop/main.js` 中 `overlayUrl(...)` 辅助函数已存在，用于拼接本地 server 地址。

### 2.2 硬阻塞（原计划遗漏，必须优先解决）
1. **`serveStatic` 不支持 Range 请求**（`server.js:217-224` 一次性 `fs.readFile` 全量返回）→ 视频无法拖动进度。
2. **MIME 表缺视频类型**（`server.js:122-131` 无 `.mp4`/`.webm`/`.m3u8`/`.ts`/`.vtt`）→ 未命中 fallback 到 `text/plain`，视频直接播不了。

### 2.3 需规避的坑
1. **端口是动态的**：`main.js:1402` `findOpenPort(3000)` 递增探测，影视页 URL 必须用模块级 `mainServerPort`（`main.js:1403`），**禁止硬编码 3000**。
2. **主窗是 `transparent: true` + `frame: false`**（`main.js:1445-1457`）：挂 WebContentsView 必须显式设背景色，否则透明窗下渲染异常；bounds 需扣掉自绘标题栏 `#desktop-titlebar`（`index.html:2114-2144`）高度。
3. **命名禁忌**：`package.json:40` 有排除规则 `!public/index.*.html`，影视文件**不得使用 `index.` 前缀**。
4. **项目无 sidebar**：`switchView`/`showPage`/`data-view` 均不存在，实际是「body class + 覆盖层显隐」模式。

## 四、~~挂载方案抉择~~（**本章整体作废，2026-07-31**）

> **作废原因**：产品决策改为「双态同构 —— 同一份 DOM，全局翻转」，不再存在「第二个页面」，因此 WebContentsView / iframe 两种挂载方案均失去适用前提。详见文档头部「架构方案变更」。
>
> **取而代之的抉择项**是视频画面承载方式（方案 A 复用全屏背景层 / 方案 B 独立覆盖层），见第 1.3 节，同样由 Step 0 spike 实测决定。

<details><summary>已作废内容（存档备查）</summary>

### 方案 A：WebContentsView
- **优点**：独立渲染进程，真隔离。视频解码不会拖累 Three.js 粒子帧率；影视页崩溃不影响音乐播放。
- **缺点**：bounds 需手动计算维护；透明窗下需显式设背景色；需要 3 个 IPC 通道；窗口 resize 需同步。

### 方案 B：同源 iframe
- **优点**：实现极简，无 IPC、无 bounds 计算，与透明窗天然兼容。
- **缺点**：共用渲染进程，视频解码与 Three.js 争抢主线程。

</details>
